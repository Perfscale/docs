## Обзор

Нативный движок задаёт нагрузку одним из трёх профилей в файле конфигурации
(`-c config.yaml`):

| Профиль | Конфиг | Модель | Для чего |
|---|---|---|---|
| Фиксированный | `vus` + `duration` | Закрытая: N воркеров крутят шаги | Ровная нагрузка, soak-тесты |
| Ступенчатый | `stages:` | Закрытая: число VU меняется во времени | Разгон, спайк, спад |
| Arrival-rate | `arrival:` | Открытая: итерации стартуют по расписанию | «N запросов в секунду», поиск предела |

`stages` и `arrival` заменяют `vus`/`duration` (lint предупредит, если заданы
оба) и взаимоисключающие; длительность прогона — сумма длительностей стадий.
Оба работают только в нативном движке: с `--locust` отклоняются, с `--k6`
файл конфигурации игнорируется.

## Фиксированный

`vus` воркеров крутят шаги в течение `duration` — профиль по умолчанию.

```yaml
vus: 10
duration: 5m
```

## Ступенчатый разгон (`stages:`)

Целевое число VU линейно интерполируется между стадиями: первая стадия
разгоняется от 0, каждая следующая — от `target` предыдущей. Спад мягкий:
VU, который убирают, доделывает текущий шаг и выходит на границе шагов.

```yaml
stages:
  - { duration: 30s, target: 10 }  # разгон 0→10 VU
  - { duration: 1m,  target: 50 }  # разгон 10→50 VU
  - { duration: 30s, target: 0 }   # спад до нуля
```

## Arrival-rate (`arrival:`)

В закрытой модели медленная система *сама замедляет нагрузку*: каждый VU
ждёт ответа, прежде чем начать следующую итерацию, и интенсивность падает
ровно тогда, когда системе плохо. Профиль arrival-rate — **открытая модель**:
движок держит расписание «итераций в секунду» и масштабирует пул воркеров,
чтобы успевать. Новые итерации стартуют вовремя, даже если система
замедлилась, — как реальные пользователи, которые продолжают приходить.

```yaml
arrival:
  max_vus: 100              # потолок пула воркеров — обязателен, ≥ 1
  pre_allocated_vus: 10     # воркеров на старте (по умолчанию 1); пул растёт до max_vus по мере нужды
  stages:
    - { duration: 30s, rate: 5 }    # разгон 0→5 итераций/с
    - { duration: 1m,  rate: 20 }   # разгон 5→20 итераций/с
```

`rate` линейно меняется между стадиями, начиная с 0; дроби допустимы
(`0.5` = одна итерация раз в 2 с). Для **постоянной** интенсивности начните
с очень короткой стадии на целевом значении и держите его:

```yaml
arrival:
  max_vus: 256
  pre_allocated_vus: 256
  stages:
    - { duration: 1ms, rate: 1000 }   # сразу 1000/с
    - { duration: 5m,  rate: 1000 }   # держим
```

### Отброшенные итерации

Если итерации пора стартовать, а все `max_vus` воркеров заняты (ещё одна
может подождать в очереди), итерация **отбрасывается**: она считается в
метрике `dropped_iterations`, а предупреждение пишется не чаще раза в 5 с.
Если метрика растёт — поднимите `max_vus` или снизьте интенсивность. Либо
считайте интенсивность, на которой начинаются отбросы, пределом системы.

`dropped_iterations` публикуется всегда, даже при 0, поэтому гейт
срабатывает и на чистых прогонах:

```yaml
after:
  - use: std/thresholds@v1
    with:
      dropped_iterations: ["count==0"]
```

> **С v0.29.0** итерации отбрасываются только при реально занятом пуле.
> Раньше на высокой интенсивности они отбрасывались и при простаивающих
> воркерах (планировщик выдаёт итерации пачками), поэтому расписание на
> 10 000/с могло выдавать намного меньше. Если старый прогон показывал много
> отбросов при низкой загрузке воркеров — перезапустите его на v0.29.0+.

### Как читать латентность в открытой модели

`http_req_duration` — чистое время сервера, только для запросов, которые
реально стартовали. При перегрузке он продолжает выглядеть здоровым, пока
пользователи ждут. Прогоны arrival записывают и вторую половину картины:

| Метрика | Что измеряет |
|---|---|
| `engine_arrival_queue_wait_ms` | Задержка от запланированного до фактического старта итерации — очередь, которую классические метрики латентности не видят (coordinated omission) |
| `engine_arrival_iteration_ms` | Ожидание в очереди + тело итерации, от *запланированного* старта — сквозная латентность глазами пользователя |
| `dropped_iterations` | Итерации, которые не смог стартовать ни один воркер |

Оценивайте перегруженный arrival-прогон по всем трём сразу.

## Что показывает итог прогона

Для прогонов `stages`/`arrival` строка `vus` в итоге показывает
наблюдаемую конкурентность (`vus....: <last> min=<min> max=<max>`),
периодическая строка `[stats]` получает поле `vus=N`, а экспорт итога
содержит `vus: null` и `duration`, равную сумме стадий.

Длительности стадий используют грамматику `"500ms"` / `"30s"` / `"1m30s"` /
`"1h"` и проверяются строго: нераспознанная или нулевая длительность
стадии роняет прогон и `perfscale lint`.
