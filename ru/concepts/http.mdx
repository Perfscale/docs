## Обзор

Шаг `std/http@v1` нативного движка выполняет один HTTP-запрос за итерацию:
любой метод, заголовки, тело, multipart-загрузки, таймаут на запрос и
опциональный пропуск проверки TLS (`insecure: true`). Статусы ≥ 400,
транспортные ошибки и таймауты считаются неудачными запросами в
`http_req_failed`.

## Пулы соединений

`pool: per-vu` (по умолчанию) привязывает каждый VU к одному шарду
HTTP-клиента (по шарду на доступное CPU, максимум 16), поэтому VU держит
тёплый keep-alive пул между итерациями без конкуренции за блокировку пула.
`pool: shared` переводит всех VU на один глобальный для процесса клиент:
максимальное переиспользование соединений к одному endpoint ценой
конкуренции за блокировку при очень большом числе VU.

`pool: dedicated` выдаёт каждому VU собственный HTTP-клиент, созданный при
первом запросе VU и живущий до его выхода — режим для сценариев «N
виртуальных пользователей = N открытых keep-alive соединений». Шардовые пулы
держат не более 64 простаивающих соединений на хост на шард, поэтому после
~`шарды × 64` VU простаивающее соединение VU вытесняется между запросами и
каждый запрос переподключается; режим dedicated снимает этот предел. Время
обдумывания (`std/sleep@v1`) соединение не закрывает; клиенты удаляются при
выходе VU (фиксированные, staged и arrival-rate прогоны одинаково). TCP/TLS
connect при этом происходит один раз на VU: первый запрос включает его,
последующие нет. Соединения, простаивающие дольше 60 с, пересоздаются, как и
в других режимах пула.

## Исходные IP

На один кортеж (исходный IP, IP назначения, порт назначения) приходится
только диапазон эфемерных портов (~28k), поэтому одна машина с одним адресом
упирается в предел ниже ~64k одновременных соединений на endpoint.
`source_ips` умножает этот бюджет, привязывая исходящие соединения к
нескольким локальным адресам — отдельные IP или CIDR-префиксы, IPv4 и IPv6:

```yaml
steps:
  - name: api
    use: std/http@v1
    with:
      url: http://target:8080/api
      source_ips: ["10.0.0.2", "10.0.0.16/28", "fd00::/120"]
```

Семантика:

- CIDR раскрывается во все адреса префикса; суммарный список ограничен 4096
  адресами — при превышении lint и валидация прогона падают с ошибкой
  «сузьте префикс».
- Виртуальный пользователь `i` привязывается к `ips[(i-1) % n]` — стабильно
  между итерациями, поэтому каждый VU держит один тёплый keep-alive пул в
  своём клиенте (шард, исходный IP). В режиме `pool: dedicated` собственный
  клиент VU привязывается к его адресу — ключ становится (vu_id, адрес).
- Клиенты создаются лениво, по факту использования пары (шард, адрес) —
  большой список не выделяет заранее тысячи пулов.
- Первый запрос прогона логирует, сколько исходных адресов активно.

Адреса должны существовать на интерфейсах генератора нагрузки. Linux по
умолчанию маршрутизирует весь 127/8 на loopback; на macOS алиасы добавляются
явно (`sudo ifconfig lo0 alias 127.0.0.2 up`). Для реальной генерации с
нескольких IP назначьте адреса на сетевой интерфейс (или используйте
несколько машин).
