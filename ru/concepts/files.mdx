## Обзор

Нативные тесты умеют читать файлы фикстур, извлекать подзначения из
JSON-документов и сохранять ответы на диск. Это покрывают три **файловых
шага**:

| Шаг | Назначение |
|---|---|
| `std/file-read@v1` | Прочитать файл (текст или base64) в output шага, опционально извлекая JSON-подзначение через `query` |
| `std/file-write@v1` | Записать содержимое в файл; с `query` — read-modify-write установка по пути внутри JSON-документа |
| `std/read-json@v1` | Прочитать и распарсить JSON-файл; кешируется **распарсенный документ**, а не только байты |

Все файловые шаги **fail-closed**: прогон должен явно включить
`allow_file_actions: true` в конфиге, а пути подчиняются ограничению
`fs_root`.

Чтения обслуживаются **общим на процесс кешем**, ревалидируемым по
`(mtime, size)` файла при каждом обращении — первая итерация платит чтение
с диска (а для `read-json` — и парсинг); каждая следующая итерация всех VU
попадает в RAM, а файл, изменённый между прогонами долгоживущего агента,
подхватывается автоматически. `std/read-json@v1` и библиотека
`@std/json@v1` делят один и тот же кеш.

**Доступность:** `std/read-json@v1` и параметр `query` — **v0.28.0+**;
базовые шаги `file-read` / `file-write` доступны в более ранних релизах.

## `std/file-read@v1`

Читает файл и отдаёт его содержимое следующим шагам:

```yaml
steps:
  - name: load payload
    use: std/file-read@v1
    with: { path: ./fixtures/payload.json }
    outputs: payload

  - name: send it
    use: std/http@v1
    with:
      method: POST
      url: "https://api.example.com/items"
      headers: { content-type: application/json }
      body: "${{ payload.content }}"
    check:
      status: 201
```

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `path` | string | **обязателен** | Файл для чтения |
| `encoding` | string | `text` | `text` (файл должен быть валидным UTF-8) или `base64` (бинарное содержимое) |
| `query` | string | — | jq-style путь (v0.28.0+, см. ниже); содержимое парсится как JSON, и подзначение по пути становится всем output'ом шага |

**Output** (доступен через `outputs` / `__last__`):

```json
{ "content": "...", "size": 1024, "path": "./fixtures/payload.json" }
```

С заданным `query` output — это извлечённое JSON-подзначение напрямую:
`${{ payload }}` *и есть* значение по пути.

Заметки:

- Не-UTF-8 файл с `encoding: text` роняет шаг — для бинарного содержимого
  используйте `encoding: base64`.
- С `query` невалидный JSON роняет шаг; отсутствующий путь тоже (ошибка
  называет упавший сегмент) — если только сегмент не несёт суффикс `?`,
  который резолвит промах в `null`.
- `${{ payload.content }}` копирует содержимое в запрос — кеш экономит
  чтения с диска, а не копию на запрос. Держите фикстуры маленькими под
  высоким RPS.
- Для *загрузки* файлов предпочтительнее параметр `multipart` у
  `std/http@v1`.

## `std/file-write@v1`

Пишет содержимое в файл — обычно чтобы сохранить ответ предыдущего шага:

```yaml
steps:
  - name: fetch report
    use: std/http@v1
    with: { url: "https://api.example.com/report" }
    outputs: resp

  - name: save it
    use: std/file-write@v1
    with:
      path: ./out/report.json
      content: "${{ resp.body }}"
```

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `path` | string | **обязателен** | Файл для записи (родительский каталог должен существовать) |
| `content` | string | **обязателен** | Данные для записи; плейсхолдеры `${{ ... }}` делают `${{ resp.body }}` типичным payload'ом |
| `encoding` | string | `text` | `text` пишет строку как есть; `base64` сначала декодирует её |
| `append` | boolean | `false` | Дописывать вместо перезаписи |
| `query` | string | — | jq-style путь (v0.28.0+): read-modify-write — загрузить JSON-файл, установить `content` по пути, записать документ обратно |

**Output**: `{ "path": <string>, "size": <записано байт> }`

Заметки:

- Запись в путь, закешированный `std/file-read@v1`, автоматически
  инвалидирует эту запись кеша.
- С `append: true` каждый вызов — одиночная `O_APPEND`-запись, так что
  конкурентные VU не перемешивают содержимое посередине; порядок между VU
  не определён.
- С `query` (установка по пути): `content`, парсящийся как JSON,
  сохраняется как JSON (остальное — как строка); промежуточные
  объекты/массивы создаются, как в jq; индекс массива должен быть в
  границах или ровно равен длине массива (**добавление** в конец — индекс
  дальше роняет шаг); отсутствующий файл стартует с пустого документа;
  существующее не-JSON содержимое роняет шаг. `query` не сочетается с
  `append` и `encoding: base64`.

## `std/read-json@v1`

Читает и парсит JSON-файл — структурный sibling `std/file-read@v1`
(**v0.28.0+**). Распарсенный документ кешируется на весь процесс, так что
итерации после первой пропускают и чтение с диска, и парсинг:

```yaml
steps:
  - name: users fixture
    use: std/read-json@v1
    with: { file: ./fixtures/users.json, query: ".users[0]" }
    outputs: user

  - name: log in
    use: std/http@v1
    with:
      method: POST
      url: "https://api.example.com/login"
      body: '{"token": "${{ user.token }}"}'
```

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `file` | string | **обязателен** | JSON-файл для чтения |
| `query` | string | — | jq-style путь, выбирающий подзначение |

**Output**: распарсенный JSON-документ или подзначение по `query`.

Невалидный JSON роняет шаг с понятным сообщением; так же ведёт себя
отсутствующий путь `query` (ошибка называет упавший сегмент), если сегмент
не несёт `?`.

## Грамматика jq-style `query`

Одна грамматика управляет `query` у `std/read-json@v1`, параметром `query`
у `std/file-read@v1` / `std/file-write@v1` и путями внутри интерполяции
`${{ ... }}` (всё — v0.28.0+). Это подмножество jq *путей* — без пайпов,
фильтров и функций:

- Опциональная ведущая `.`, затем сегменты вида `.key`, `["key"]` или `[0]`.
- Точечный сегмент из одних цифр тоже индексирует массив, так что
  `posts.0.id` ≡ `.posts[0].id`.
- Суффикс `?` на сегменте делает его **толерантным** — промах резолвится в
  `null` вместо падения шага (например, `.users?[0]`).

## Пути в телах в интерполяции

Та же грамматика расширяет плейсхолдеры `${{ }}` (v0.28.0+): путь,
продолжающийся за *строковым* листом — HTTP-ответом `body`, `content`
файлового шага — парсит его как JSON по требованию и спускается в документ:

```yaml
steps:
  - use: std/http@v1
    with: { url: "https://api.example.com/feed" }
    outputs: feed                       # output: { status, body, headers, ... } — body это строка

  - use: std/http@v1
    with:
      url: "https://api.example.com/posts/${{ feed.body.posts[0].id }}"
```

Движок парсит `feed.body` как JSON по требованию и спускается внутрь.
`${{ feed.body.posts[0].id }}` и точечный вариант
`${{ feed.body.posts.0.id }}` взаимозаменяемы. Как и любой плейсхолдер,
промах резолвится в **пустую строку** — прогон не падает; гейтайте значение
через `check:`, когда отсутствие должно быть ошибкой.
