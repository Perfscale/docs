## Обзор

Прогон наблюдаем, пока он ещё подаёт нагрузку — а не только когда придёт
итоговая сводка. Движок на машине каждые несколько секунд снимает кумулятивный
снапшот всех собранных метрик и стримит его на платформу; страница прогона
рисует графики по мере прихода сэмплов, а тот же поток питает дашборд
**Metrics**, Prometheus-совместимый query API и Remote Write. Никаких
InfluxDB и внешних коллекторов — поток встроен в сам прогон.

## Как включить

Добавьте блок `report:` с `during_run: true` в **Configuration**, с которой
запускается тест, — в редакторе конфигураций для этого есть сниппет
**During-run metrics**:

```yaml
report:
  during_run: true        # по умолчанию false — только итоговая сводка
  interval_ms: 5000       # интервал снапшотов/флаша, минимум 100 мс
  batch_size: 500         # запечатать батч при таком числе сэмплов
  max_cpu_percent: 90     # CPU-гейт; 0 отключает его (Linux)
  max_pending: 24         # ограниченная очередь — при переполнении выбрасывается САМЫЙ СТАРЫЙ снапшот
```

Остальное делает агент: он аутентифицирует поток машинным токеном и метит
каждый сэмпл лейблами `task_id` и `machine_id`, так что распределённый прогон
чисто раскладывается по генераторам нагрузки.

Стриминг работает для **нативного движка**. Скрипты k6, JMeter и Locust
по-прежнему дают нормализованную итоговую сводку и живые логи, но during-run
сэмплы не стримят.

## Что шлёт движок

Каждый снапшот разворачивает все семейства метрик прогона в сэмплы по
конвенциям Prometheus (длительности в **секундах**):

| Метрика движка | Отправляемые сэмплы |
|---|---|
| Гистограмма (`http_req_duration`, свои тренды) | `<name>{quantile="0.5"/"0.9"/"0.95"/"0.99"}`, `<name>_count`, `<name>_sum` |
| Счётчик | `<name>_total` |
| Доля ошибок (`http_req_failed`, …) | `<name>_total` (вызовы), `<name>_failed_total` (ошибки) |
| GPU-гауг (при `gpu.enabled`) | `gpu_utilization_pct`, `gpu_memory_used_mib`, `gpu_temperature_c`, `gpu_power_w` по устройствам — на Apple Silicon также `ane_power_w`, `cpu_power_w`, `package_power_w` |

Пользовательские метрики ваших шагов — латентность gRPC, время запросов к БД,
`llm_ttft_ms`, счётчики WebSocket — подхватываются автоматически; настраивать
ничего не нужно.

Снапшоты **кумулятивные** (гистограммы и счётчики не сбрасываются в середине
прогона); платформа диффает соседние снапшоты, чтобы рисовать значения за
интервал. GPU-гауги — точечные значения и чартятся как есть.

## Как ведёт себя доставка

Батч запечатывается при `batch_size` сэмплов или по тику `interval_ms` — что
наступит раньше — и уходит на платформу со строго возрастающим `seq`.
Ингест дедуплицирует по `(task_id, seq)`, так что переотправленный батч
никогда не задвоит данные. Когда прогон завершается, всё оставшееся в очереди
сливается (финальный дренаж, предел 30 секунд), а следом приходит обычная
итоговая сводка.

## Защита генератора нагрузки

Shipper живёт по одному правилу: **генерация нагрузки всегда важнее
отчётности о ней.**

- Движок никогда не блокируется на метриках — снапшоты идут через
  ограниченный канал, а переполненный канал выбрасывает снапшот, а не
  тормозит виртуальных пользователей.
- **CPU-гейт**: пока busy-CPU машины держится на уровне `max_cpu_percent`
  или выше (по умолчанию 90%, Linux), shipper придерживает все батчи и
  складывает входящие снапшоты в очередь — ноль отправок, пока машина не
  придёт в себя, затем накопленные точки уходят по порядку. Если генератор
  упёрся в потолок, perfscale замолкает, а не дерётся с виртуальными
  пользователями за последние ядра.
- Очередь **ограничена** (`max_pending`, по умолчанию 24): при переполнении
  выбрасывается САМЫЙ СТАРЫЙ снапшот и считается в
  `perfscale_report_dropped_snapshots_total{reporter="serve"}` — свежие
  данные всегда ценнее протухшего бэклога, а так как каждый снапшот
  кумулятивный, следующий доставленный снапшот восстанавливает полные
  значения, и информация не теряется окончательно.
- Сетевые ошибки, 5xx и 429 ретраят тот же батч с тем же `seq`
  (экспоненциальный бэкофф); любой другой 4xx выбрасывает отравленный батч
  и идёт дальше.

## Стриминг в свои системы наблюдаемости

Помимо потока на платформу, движок может пушить те же живые метрики напрямую
в ваш стек, пока прогон выполняется, — объявите стриминг-репортеры в
`report.reporters`:

```yaml
report:
  reporters:
    - use: std/report/prometheus-rw@v1   # Prometheus remote write (Snappy + protobuf)
      during_run: true
      interval_ms: 5000                  # каденс этого репортера
      labels: { env: staging }           # штампуется на каждой экспортируемой серии
      max_series: 10000                  # защита от кардинальности (по умолчанию)
      with:
        url: http://vm:8428/api/v1/write
        histogram: classic               # classic (по умолчанию) или native
        batch_size: 500
        max_pending: 24                  # ограниченная очередь, drop-oldest при переполнении
        retry: { max_attempts: 5, backoff: "1s..30s" }
        final_timeout: 30s               # граница синхронного финального флаша
    - use: std/report/otel@v1            # OTLP/gRPC
      during_run: true
      with:
        endpoint: http://otel-collector:4317
```

Семантика — для каждого репортера независимо от остальных (медленный или
мёртвый бэкенд никогда не блокирует виртуальных пользователей и другие
репортеры):

- **Маппинг метрик** — счётчики/rate становятся монотонными суммами, гауги —
  гаугами, длительности — гистограммами. Prometheus remote write по
  умолчанию отдаёт **классические** серии `_bucket{le}`/`_sum`/`_count`;
  `with.histogram: native` включает нативные гистограммы Prometheus. OTLP
  экспортирует **экспоненциальные гистограммы** с кумулятивной
  темпоральностью. Ни один экспортёр не шлёт клиентские квантильные серии —
  бэкенд считает корректные квантили между воркерами по бакетам:

  ```promql
  histogram_quantile(0.95, sum by (le) (rate(http_req_duration_bucket[1m])))
  ```

- **Лейблы** — мёржатся в порядке **шаг > репортер > прогон**
  (`report.labels`). Значения интерполируют `${{ inputs.* }}` /
  `${{ env.* }}` один раз до прогона. `run_id` и `worker` зарезервированы и
  всегда выставляются движком — распределённый прогон чисто раскладывается
  по `worker`.
- **Кардинальность** — `max_series` (по умолчанию 10000) ограничивает число
  различных выходных серий репортера, включая классические бакеты. Серии
  сверх лимита детерминированно выбрасываются и считаются в
  `perfscale_report_dropped_series_total{reporter="…"}`; прогон продолжается.
- **Батчинг и backpressure** — у каждого репортера своя ограниченная
  очередь (`with.max_pending`, по умолчанию 24); батч запечатывается при
  `with.batch_size` или по тику `interval_ms`. Переполнение выбрасывает
  САМЫЙ СТАРЫЙ снапшот
  (`perfscale_report_dropped_snapshots_total{reporter="…"}`); следующий
  кумулятивный снапшот восстанавливает значения.
- **Ретраи** — сетевые ошибки, 429 и 5xx (и transient gRPC-статусы для
  OTLP) ретраятся с экспоненциальным бэкоффом (`with.retry.max_attempts`,
  по умолчанию 5; `with.retry.backoff`, по умолчанию `"1s..30s"`; подсказка
  сервера `Retry-After` имеет приоритет). Любой другой 4xx — отравленный
  батч: выбрасывается с предупреждением, без ретраев.
- **Финальный флаш** — по завершении прогона каждый репортер синхронно
  отправляет терминальный кумулятивный снапшот, ограниченный
  `with.final_timeout` (по умолчанию 30 с). Неудачный или просроченный флаш
  пишет предупреждение, но никогда не меняет exit code прогона.

Семейства счётчиков `perfscale_report_dropped_series_total`,
`perfscale_report_dropped_snapshots_total` и
`perfscale_report_errors_total` сами экспортируются в каждый бэкенд с
лейблом `reporter`, так что дропы и ошибки доставки видны в той же Grafana,
куда вы отправляете метрики нагрузки.

Стриминг-репортеры — фича **open-source движка** (нативный движок,
**следующий релиз**). `during_run: true` на final-only репортере
(JSON/JUnit/HTML/WASM) — ошибка конфигурации, пойманная до начала прогона.

Полный инженерный контракт — в OSS-справочнике:
[During-run metrics](/docs/oss/core/metrics#during-run-metrics-reportduring_run).

## Как читать метрики

- **Страница прогона** — графики рисуются по мере прихода сэмплов:
  перцентили задержки, пропускная способность, доля ошибок, кривые GPU. Без
  обновления страницы и ожидания сводки.
- **Дашборд Metrics** — определяет протокол прогона по стримящимся
  семействам и подставляет подходящий набор плиток
  ([Протокольные метрики](/docs/concepts/protocol-metrics)).
- **Grafana** — платформа отдаёт Prometheus-совместимый query API. Settings →
  **Integrations** показывает URL датасорса
  (`<инстанс>/api/v1/integrations/prometheus`); аутентификация — персональным
  API-токеном из Settings → **Keys** (`Authorization: Bearer psk_…`).
  Запрашивайте как любой Prometheus — `rate(http_req_duration_count[1m])`,
  раскладка по `machine_id` и т.д.
- **Remote Write** — удобнее своё хранилище? Settings → **Integrations** →
  **Prometheus Remote Write** пушит каждый принятый сэмпл в ваш Prometheus,
  Mimir, VictoriaMetrics или Grafana Cloud, с опциональной basic/bearer
  аутентификацией.
