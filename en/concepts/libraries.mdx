## Overview

Every perfscale payload can embed `${...}` generator tokens — `${seq}`,
`${uuid}`, `${rand(1,100)}` — that the engine expands when a message is
sent. The built-in set is deliberately small. **Libraries** are the
extension point: a library is a WASM component (or a native built-in) that
contributes its own functions, callable from any payload as
`${alias.fn(...)}`:

```yaml
libraries:
  - use: '@std/random@v1'        # built-in, no files needed
    capabilities: []             # required key — [] means "no grants"

steps:
  - use: std/db-query@v1
    with:
      query: INSERT INTO orders (id, code, who) VALUES (?, ?, ?)
      params:
        - "${random.ulid()}"
        - "${random.pattern("ORD-####-^^")}"
        - "${random.email()}"
```

Real UUID v4/v7, ULIDs, faker-style names and emails, weighted picks,
pattern fills — without patching the engine, and with the same `${...}`
syntax across every protocol (HTTP, WebSocket, gRPC, GraphQL, raw TCP/UDP,
LLM prompts, DB parameters).

## Declaring libraries

`libraries:` is accepted in the config file, the test file, or both
(declarations concatenate across `import:`; a duplicate alias is a
validation error):

```yaml
libraries:
  - use: '@std/random@v1'        # built-in; default alias: random
    capabilities: []
  - use: '@std/random@v1'
    as: ids                      # second instance, tokens: ${ids.fn(...)}
    capabilities: []
  - use: ./libs/fixer-ids.wasm   # local WASM component, path relative to this file
    capabilities: []
  - use: 'https://vendor.example.com/faker-1.2.0.wasm'
    sha256: '9f2c…64 hex…'       # required for HTTPS sources
    capabilities: []
  - use: 'git+https://github.com/org/repo.git@v1.2.3#libs/fixer-ids.wasm'
    capabilities: []
```

- `use:` — a built-in `@ns/name@vN` reference (quotes required: `@` is a
  reserved YAML indicator), a local `.wasm` path, an HTTPS URL, or a
  `git+<repo>@<ref>#<path>` reference.
- `as:` — the token prefix. Default is the library's own name.
- `capabilities:` — explicit sandbox grants, see below.
- `with:` — JSON config passed to the library's `init()`; may use
  `${{ env.X }}` so secrets stay masked in logs.

Remote sources (`https://`, `git+`) are **never fetched at run time**.
`perfscale install` fetches each remote library once, verifies its digest,
stores it in a content-addressed cache, and writes a `perfscale.lock` next
to the declaring file — commit the lock. `run` and `lint` then resolve
everything **fully offline**; a missing lock entry is a hard error that
says to run `perfscale install` (`--refresh` re-resolves git refs).

## Token semantics

- Built-in tokens (`${seq}`, `${rand}`, …) match first and are unchanged;
  an alias may not shadow them.
- Unknown alias → the token stays verbatim (backward compatible; `perfscale
  lint` flags it). Known alias + unknown function or bad arguments → the
  **step fails**. A typo must not ship silently into a payload.
- Arguments map text → JSON by a fixed contract: split on commas outside
  double quotes, trim, strip one pair of quotes, parse as JSON if possible.
  `int(1,100)` passes two numbers; `pick(a|b|c)` passes one string.
- Any function's optional trailing `key` argument **memoizes** the result
  within one message: `${random.uuid4(order)}` appearing twice in one
  message yields one id; the next message generates a fresh one.
- `seed: 42` in the config makes a run reproducible — every library
  instance derives its seed as `hash(seed, vu_id, conn_seq)`.
- A failed call (guest error, trap, timeout) fails the step with the cause
  recorded — a load test never sends wrong data and reports green.

## The `@std/random@v1` built-in

Ships with the engine — no WASM, no install, no capabilities. Every
function accepts the optional trailing memo `key`:

| Function | Returns |
|---|---|
| `uuid4([key])` / `uuid7([key])` | Random v4 / time-ordered v7 UUID |
| `ulid([key])` | 26-char Crockford-base32 ULID |
| `nanoid([len], [key])` | URL-safe id (default len 21) |
| `int(a, b, [key])` | Random integer in `[a, b]` |
| `float(a, b, [dp], [key])` | Random float, `dp` decimals |
| `pick(a\|b\|c, [key])` | Random pick among `\|`-separated options |
| `weighted(a:10\|b:90, [key])` | Weighted random pick |
| `seq(name)` | Named monotonic counter, starts at 1 |
| `pattern("ORD-####-????")` | Template fill: `#`→digit, `?`→a-z, `^`→A-Z, `*`→alphanumeric |
| `first_name()` / `last_name()` / `name()` | Random names |
| `username()` / `email()` / `company()` | Random username / email / company |
| `lorem([words])` | Lorem-ipsum words (default 5) |
| `phone()` | Random phone number |
| `date(a, b)` / `timestamp(a, b)` / `datetime(a, b)` | Random dates and timestamps in a range |

## The `@std/json@v1` built-in

**v0.28.0+.** Ships with the engine — no WASM, no install — and reads JSON
files into generator tokens; the structured counterpart of the
`std/read-json@v1` step (see [File steps](/docs/concepts/files)):

```yaml
libraries:
  - use: '@std/json@v1'          # default alias: json
    capabilities: []

steps:
  - use: std/http@v1
    with:
      method: POST
      url: "https://api.example.com/login"
      body: '{"token": ${json.read("users.json", ".users[0].token")}}'
```

| Function | Returns |
|---|---|
| `read(file)` | The whole parsed document, as a compact JSON string |
| `read(file, query)` | The subvalue at a jq-style path (`.posts[0].id` ≡ `posts.0.id` — the same grammar as the file steps' `query:`); a string leaf verbatim, other values as compact JSON |
| `pick(file)` / `pick(file, index)` | An element of the JSON array in `file` — uniformly random per message, or the deterministic `index` modulo the array length; a string element verbatim, other values as compact JSON |

Notes:

- Parsed documents come from the **process-wide cache shared with
  `std/read-json@v1`**, revalidated by `(mtime, size)` — the first call pays
  the disk read and parse, every later call (step or library) hits RAM.
- **Fail-closed**: the run must set `allow_file_actions: true` (and paths
  honour `fs_root`), exactly like the `std/file-*@v1` steps.
- Error semantics differ from the step: a missing mandatory path segment is
  a token-expansion error naming the segment (fails the step it appears in),
  while a `?`-tolerant miss (`json.read("f.json", ".users?[0]")`) resolves
  to an **empty string** — interpolation-friendly, where the step yields a
  `null` output.
- `pick` respects seeded runs: the random index derives from the engine's
  deterministic pipeline (FNV-1a over the per-call seed — which folds in the
  run `seed:` — plus the message sequence and file path), so a `seed:` run
  replays the exact pick sequence, unseeded runs are random, and repeat
  calls within one message pick the same element. A document that is not a
  JSON array, an empty array, or a non-integer `index` is a call error.

Like `@std/random@v1`, `@std/json@v1` is **opt-in**: nothing is
auto-registered — without the `libraries:` entry above, `${json.*}` tokens
do not resolve.

## Config extensions: library-owned top-level keys

A WASM library can **claim one top-level config key** and validate its value
against a JSON Schema the library itself declares (issue #10) — for example
a connection profile shared by all of the library's functions:

```yaml
libraries:
  - use: ./configlib.wasm
    capabilities: []
configlib:                    # the key the library's config-schema claims
  endpoint: https://api.test  # validated against the library's schema
  pool_size: 4
```

The library declares the claim with a schema like:

```json
{ "key": "configlib",
  "schema": { "type": "object",
              "properties": { "endpoint": { "type": "string" },
                              "pool_size": { "type": "integer", "minimum": 1 } },
              "required": ["endpoint"],
              "additionalProperties": false } }
```

Semantics:

- At **lint and run start** the engine loads the declared libraries,
  registers their claimed keys, and validates each block against the
  library's schema — fail-fast, with schema errors spelled out.
- The block is **optional**: when the key is absent from the config, the
  library's `extensions` simply does not contain it — treat it as
  "feature off" in `init()`.
- Every top-level key no loaded library claims is still a **hard error** —
  the unknown-key typo guard lives in this check.
- Keys follow the alias grammar `[a-z][a-z0-9_]*`. A key colliding with a
  built-in config key, or claimed by **two libraries** in one run, is a hard
  error.
- The validated block reaches the guest in the run settings' `extensions`
  object — in the TS SDK,
  `defineLibrary({ configSchema: { key, schema }, ... })` declares the block
  and handlers read it as `ctx.settings.extensions["configlib"]`;
  `perfscale-library-build` picks the `perfscale-library-config` world
  automatically when `configSchema` is present. In Rust, the main
  `export_library!` macro currently targets the base world — export
  `config-schema` directly against the `perfscale-library-config` WIT world
  to ship a schema.

Not in v1: interpolation inside extension blocks, and schema evolution
across `perfscale.lock` pins.

## Capabilities and the sandbox

Custom libraries run in a wasmtime sandbox under a **fail-closed**
capability model: the component's WASI imports are checked against the
`capabilities:` grant in YAML, and the host connects exactly the
intersection. A component importing more than granted is a hard load error.

| Capability | Host provides | Boundaries |
|---|---|---|
| `fs` | `wasi:filesystem` preopens | only paths under `fs_root`, read-only |
| `clock` | `wasi:clocks` | wall time also arrives via the call context |

Any non-empty grant requires `allow_library_capabilities: true` in the
config — the same fail-closed pattern as `allow_file_actions`. Raw sockets
are never provided. `wasi:random` is not provided either: libraries draw
all randomness from the seeded PRNG their SDK exposes, which is what makes
`seed:` runs reproducible. Per-call fuel and a wall-time timeout bound what
a runaway component can do on the hot path, and time inside a library call
is counted in the enclosing step's duration — library cost shows up in
metrics, never hidden.

## Library lifecycle on the platform

When the load generator is a platform machine (an agent), the library cache
is managed remotely — the flow mirrors the CLI but is driven from the
controlplane:

1. **Install** — the controlplane pushes the library to the machine
   (UI-driven, over the agent API): the artifact is fetched once,
   digest-verified, and stored in the agent's content-addressed cache
   (`<cache>/libraries/<sha256>.wasm`). For HTTPS installs the `sha256` pin
   is optional: when present it is verified (a mismatch is a hard error),
   when absent the digest is computed from whatever the URL serves.
2. **Install-time burn** — a freshly installed library is also AOT
   precompiled to `<sha256>.cwasm`. The burn is *advisory*: a precompile
   failure downgrades to a warning, never a failed install.
3. **Auto-burn before every run** — the advisory burn can be missing (a
   failed burn, a cache copied without `.cwasm` files, an artifact burned by
   an older engine), so the agent re-checks before each test run and
   precompiles any digest-pinned library whose `.cwasm` is missing or
   stale — Cranelift compilation never lands inside the measured run. A
   failure here degrades to a run-log warning and run-time compilation,
   never a failed run.
4. **Uninstall + deburn** — removing a library from a machine deletes both
   the `.wasm` artifact and its `.cwasm` burn from the cache, so nothing
   stale is left behind. Built-in `@std` libraries ship inside the engine
   binary and can never be uninstalled.

## Writing your own library

One shape, three languages — each SDK hides the WIT plumbing and gives you
a seeded PRNG (bit-identical across SDKs and the engine), `memo()` for
per-message reuse, argument helpers, and a runtime-free test harness:

- **Rust** — [`perfscale-library-sdk`](https://github.com/Perfscale/perfscale/tree/main/crates/perfscale-library-sdk),
  builds to `wasm32-wasip2` with no extra toolchain. The
  [library-random](https://github.com/Perfscale/library-random) repo — the
  WASM port of `@std/random` — doubles as the author template.
- **TypeScript / JavaScript** —
  [`@perfscale/library-sdk`](https://github.com/Perfscale/sdk-libraries):
  `defineLibrary({...})`, then `npx perfscale-library-build mylib.ts -o
  mylib.wasm` (jco componentize). Note that jco components always import
  `wasi:filesystem`, so TS libraries need the `fs` grant even when pure.
- **Go** — a documented TinyGo recipe in the same
  [sdk-libraries](https://github.com/Perfscale/sdk-libraries) repo
  (experimental).

## Availability and linting

Libraries are part of the test/config YAML, so the same definition runs
from the CLI and on your machines. The `@std/random` built-in needs no
files at all; custom WASM components must be present on the load generator
(relative paths resolve against the declaring file, remote refs come from
the install cache). `perfscale lint` loads declared libraries and validates
every `${alias.fn(...)}` token against the functions they actually export —
typos are caught before the run.

The full config surface is in the engine's
[YAML reference](https://github.com/Perfscale/perfscale/blob/main/docs/yaml-reference.md);
the design rationale is [RFC 005](https://github.com/Perfscale/perfscale/blob/main/rfcs/005-libraries.md).
