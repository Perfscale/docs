## Overview

A run is observable while it is still applying load — not just when the
end-of-run summary lands. The engine on the machine takes a cumulative
snapshot of every metric the run has collected every few seconds and streams
it to the platform; the run page draws its charts as the samples arrive, and
the same feed powers the **Metrics** dashboard, the Prometheus-compatible
query API, and Remote Write. No InfluxDB, no extra collector — the stream is
built into the run itself.

## Turning it on

Add a `report:` block with `during_run: true` to the **Configuration** the
test runs with — the configuration editor has a **During-run metrics** snippet
for exactly this:

```yaml
report:
  during_run: true        # default false — end-of-run summary only
  interval_ms: 5000       # snapshot/flush interval, min 100 ms
  batch_size: 500         # seal a batch at this many samples
  max_cpu_percent: 90     # CPU gate; 0 disables it (Linux)
  max_pending: 24         # bounded queue — on overflow the OLDEST snapshot is dropped
```

The agent handles the rest: it authenticates the stream with its machine
token and stamps every sample with `task_id` and `machine_id`, so a
distributed run splits cleanly per load generator.

Streaming applies to the **native engine**. k6, JMeter, and Locust scripts
still produce their normalized end-of-run summary and live logs, but do not
stream during-run samples.

## What the engine streams

Each snapshot flattens every metric family the run collected into
Prometheus-convention samples (durations in **seconds**):

| Engine metric | Shipped samples |
|---|---|
| Histogram (`http_req_duration`, custom trends) | `<name>{quantile="0.5"/"0.9"/"0.95"/"0.99"}`, `<name>_count`, `<name>_sum` |
| Counter | `<name>_total` |
| Failure rate (`http_req_failed`, …) | `<name>_total` (invocations), `<name>_failed_total` (failures) |
| GPU gauge (with `gpu.enabled`) | `gpu_utilization_pct`, `gpu_memory_used_mib`, `gpu_temperature_c`, `gpu_power_w` per device — on Apple Silicon also `ane_power_w`, `cpu_power_w`, `package_power_w` |

Custom metrics your steps emit — gRPC latencies, DB query times,
`llm_ttft_ms`, WebSocket counters — ride along automatically; nothing to
wire per metric.

Snapshots are **cumulative** (histograms and counters never reset mid-run);
the platform diffs successive snapshots to chart per-interval values. GPU
gauges are point-in-time and charted as-is.

## How delivery behaves

A batch seals at `batch_size` samples or on the `interval_ms` tick, whichever
comes first, and is POSTed to the platform with a strictly increasing `seq`.
The ingest side deduplicates on `(task_id, seq)`, so a retried batch can
never double-count. When the run ends, everything still queued is flushed
(final drain, 30-second cap), then the usual end-of-run summary follows.

## Protecting the load generator

The shipper lives by one rule: **generating load always wins over reporting
it.**

- The engine never blocks on metrics — snapshots go over a bounded channel,
  and a full channel drops the snapshot instead of slowing virtual users.
- **CPU gate**: while the machine's busy CPU sits at or above
  `max_cpu_percent` (default 90%, Linux), the shipper holds all batches and
  queues incoming snapshots — zero uploads until the machine recovers, then
  the queued points ship in order. If the generator is pinned, perfscale
  goes quiet rather than compete with the virtual users for the last cores.
- The queue is **bounded** (`max_pending`, default 24): on overflow the
  OLDEST snapshot is dropped and counted in
  `perfscale_report_dropped_snapshots_total{reporter="serve"}` — newer data
  is always more valuable than a stale backlog, and because every snapshot
  is cumulative the next delivered snapshot restores the full values, so no
  information is permanently lost.
- Network errors, 5xx and 429 retry the same batch with the same `seq`
  (exponential backoff); any other 4xx drops the poison batch and moves on.

## Streaming to your own observability backends

Beyond the platform stream, the engine can push the same live metrics
directly to your own stack while the run executes — declare streaming
reporters under `report.reporters`:

```yaml
report:
  reporters:
    - use: std/report/prometheus-rw@v1   # Prometheus remote write (Snappy + protobuf)
      during_run: true
      interval_ms: 5000                  # this reporter's cadence
      labels: { env: staging }           # stamped on every exported series
      max_series: 10000                  # cardinality guard (default)
      with:
        url: http://vm:8428/api/v1/write
        histogram: classic               # classic (default) or native
        batch_size: 500
        max_pending: 24                  # bounded queue, drop-oldest on overflow
        retry: { max_attempts: 5, backoff: "1s..30s" }
        final_timeout: 30s               # bound on the synchronous final flush
    - use: std/report/otel@v1            # OTLP/gRPC
      during_run: true
      with:
        endpoint: http://otel-collector:4317
```

Semantics, per reporter and independent of every other reporter (a slow or
dead backend never blocks the VUs or another reporter):

- **Metric mapping** — counters/rates become monotonic sums, gauges become
  gauges, durations become histograms. Prometheus remote write emits
  **classic** `_bucket{le}`/`_sum`/`_count` series by default; set
  `with.histogram: native` for Prometheus native histograms. OTLP exports
  **exponential histograms** with cumulative temporality. Neither exporter
  emits client-side quantile series — the backend computes correct
  cross-worker quantiles from the buckets:

  ```promql
  histogram_quantile(0.95, sum by (le) (rate(http_req_duration_bucket[1m])))
  ```

- **Labels** — merge in the order **step > reporter > run**
  (`report.labels`). Values interpolate `${{ inputs.* }}` / `${{ env.* }}`
  once before the run. `run_id` and `worker` are reserved and always set by
  the engine — a distributed run splits cleanly per `worker`.
- **Cardinality** — `max_series` (default 10000) caps the distinct output
  series per reporter, classic buckets included. Series beyond the cap are
  dropped deterministically and counted in
  `perfscale_report_dropped_series_total{reporter="…"}`; the run continues.
- **Batching & backpressure** — each reporter has its own bounded queue
  (`with.max_pending`, default 24) and seals batches at `with.batch_size`
  or on its `interval_ms` tick. Overflow drops the OLDEST snapshot
  (`perfscale_report_dropped_snapshots_total{reporter="…"}`); the next
  cumulative snapshot restores the values.
- **Retry** — network errors, 429 and 5xx (and the transient gRPC statuses
  for OTLP) retry with exponential backoff (`with.retry.max_attempts`,
  default 5; `with.retry.backoff`, default `"1s..30s"`; a server's
  `Retry-After` hint wins). Any other 4xx is a poison batch — dropped with a
  warning, never retried.
- **Final flush** — when the run ends, each reporter synchronously ships the
  terminal cumulative snapshot, bounded by `with.final_timeout` (default
  30s). A failed or timed-out flush logs a warning but never changes the
  run's exit code.

The `perfscale_report_dropped_series_total`,
`perfscale_report_dropped_snapshots_total` and
`perfscale_report_errors_total` counter families are themselves exported to
each backend with a `reporter` label, so drops and delivery failures are
visible in the same Grafana you send the load metrics to.

Streaming reporters are an **open-source engine** feature (native engine,
**next release**). Setting `during_run: true` on a final-only reporter
(JSON/JUnit/HTML/WASM) is a configuration error caught before the run.

The full engineering contract is in the OSS reference:
[During-run metrics](/docs/oss/core/metrics#during-run-metrics-reportduring_run).

## Reading the metrics

- **Run page** — charts draw themselves as samples arrive: latency
  quantiles, throughput, failure rate, GPU curves. No refresh, no waiting
  for the summary.
- **Metrics dashboard** — detects the run's protocol from the streamed
  families and swaps in the matching tile set ([Protocol metrics](/docs/concepts/protocol-metrics)).
- **Grafana** — the platform exposes a Prometheus-compatible query API.
  Settings → **Integrations** gives you the datasource URL
  (`<instance>/api/v1/integrations/prometheus`); authenticate with a personal
  API token from Settings → **Keys** (`Authorization: Bearer psk_…`). Query
  it like any Prometheus — `rate(http_req_duration_count[1m])`, split by
  `machine_id`, and so on.
- **Remote Write** — prefer your own store? Settings → **Integrations** →
  **Prometheus Remote Write** pushes every ingested sample to your
  Prometheus, Mimir, VictoriaMetrics, or Grafana Cloud, with optional basic
  or bearer auth.
