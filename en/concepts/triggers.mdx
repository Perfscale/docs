## Overview

A **trigger** fires a test on a schedule: a standard cron expression, a target
machine, and an optional configuration. Triggers are how nightly regression
runs, weekend soak tests, and every-fifteen-minutes probes happen without
anyone clicking **Run**.

Manage them from **Triggers** in the admin console.

## Anatomy of a trigger

| Field | Description |
|-------|-------------|
| **Name** | Display name; an optional **description** documents what the schedule is for |
| **Test** | The test to launch (required) |
| **Machine** | The load generator it runs on (required) |
| **Configuration** | Optional stored run configuration; the test's own defaults when omitted |
| **Cron** | Standard 5-field cron expression, e.g. `0 9 * * 2` — validated when you save |
| **Timezone** | IANA timezone the expression is evaluated in (default `UTC`) |

The console renders the schedule in words under the expression — localized to
the UI language — so `0 9 * * 2` reads as "at 09:00 on Tuesdays" instead of
something you have to decode mentally.

## Pause and resume

Each trigger has a GitLab-style enable toggle:

- **Enabled** — the trigger shows its **next run** and fires on schedule.
  Enabling recomputes the next run from now.
- **Paused** — the next run is cleared and nothing fires; the trigger keeps
  its schedule and history for when you resume it.

The next run is shown only while the trigger is enabled. Editing the cron
expression or timezone of an enabled trigger recomputes it, and it is
recomputed before every fire — a control-plane restart never silently skips a
scheduled run.

Need a one-off launch right now? The **run now** button fires the trigger
immediately without disturbing the schedule.

## Run history

The trigger list keeps the last launch per trigger: when it ran, the task it
created (with live status), and the last launch error if one occurred —
quota reached, overlapping run skipped, machine offline, and so on.
